Amazon S3 Files：The first and only cloud object store that provides fully-featured, high-performance file system access to your data  

**s3fs-fuse**：  
使用fuse将标准的文件操作转化为S3 API调用，缺点：比较慢，并且存在一些限制，比如无法支持文件锁，将rename转化为copy-and-delete操作  

**JuiceFS**：  
提供完整的POSIX语义，只是需要独立的元数据底层架构  

**S3 Files**：  
共享文件系统，可以访问任意的亚马逊S3数据，提供完整的文件系统语义和低延时性能，不用再对象存储和文件系统存储之间复制数据，文件与对象存储合二为一。
不在 S3 API 之上构建文件系统模拟层 ，在S3存储底层之上，直接叠加一套生产级文件系统（Amazon Elastic File System (EFS) ，EFS支持NFS v4.1 ）  

缓存架构采用双层分级设计。  能够智能将活跃工作数据集加载至高性能存储层。这一设计可为高频访问数据提供低延迟，同时让成本与实际活跃使用量成正比。读取文件时，S3 Files 以**懒加载**方式，将部分元数据与文件内容加载到高性能存储。未达到配置文件大小阈值的数据，会直接从 S3 读取，全程不占用文件系统存储资源。写入数据时，写入操作先落至高耐久的高性能存储，再同步回 S3，保障存储桶数据一致性。超过可配置闲置周期（1–365 天，默认 30 天）未被访问的数据，会自动从高性能存储层过期清理；

任意一个S3 bucket都可以作为文件系统访问，不用额外的数据迁移，通过标准的NFS文件接口进行所有的文件操作。  

AWS 在对象存储之上增加了一层基于 EFS 的文件系统访问面，使原本只能通过对象接口访问的数据，也能以目录、文件和挂载点的形式被计算节点直接使用；而文件系统与 S3 之间的数据变化，则由服务在后台自动同步。  

核心亮点[^1]：  
- **完整的POSIX兼容性**: 它**支持所有标准文件操作，包括随机写入、原子重命名、文件锁等**，突破了以往方案的关键瓶颈[^2]。其AWS官方博客也宣称，这是全球首个提供“**功能齐全**”文件系统访问能力的云对象存储服务。
- **原生NFS访问**: 只需一条简单的 `mount` 命令，即可将S3桶挂载为NFS共享，应用无需任何代码修改，就能通过标准的 `open()`、`write()` 等API直接访问S3内的数据[^3]
- **智能缓存架构**: 底层基于EFS技术，为活跃数据提供**约1ms的低延迟访问**，同时直接读取冷数据以实现高吞吐。你可以灵活控制高性能缓存层的内容（如全文件或仅元数据）[^4]
- **自动双向同步与并发访问**: 文件系统的修改会自动同步回S3桶，反之亦然。同时支持多个计算节点（EC2, EKS等）并发挂载，并通过NFS的close-to-open语义保证一致性[^5]
- **生产级稳定性与性能**: 采用与EFS相同的高可用架构，据报道支持**高达250,000次读IOPS**和**TB/s级别**的聚合吞吐量，并有成功的压力测试数据[^6]

核心机制：  
S3 Files 的设计目标，是在对象存储（S3）之上，构建一个兼具低成本和高性能的文件系统界面。它的关键在于“工作的数据”和“存储的数据”是分离的  
- **高性能缓存层**：当你通过 S3 Files 访问数据时，系统不会直接操作 S3 对象。它会将你正在处理的“热数据”和元数据暂时存放在一个由 **Amazon EFS 技术支持的高性能存储区**
- **S3 作为唯一的事实来源**：所有数据的最终、完整、权威的副本，依然保存在你的 S3 桶中。高性能缓存层只是一个暂存“工作副本”的地方[^9]
所有对文件的修改都遵循一个“暂存-提交”模型。你的操作会先在缓存层完成，系统会聚合一段时间的变更，然后以 `PUT` 操作的形式批量提交回 S3 桶

历程：这不是业界第一次尝试让 S3 以文件系统方式被访问：从早期的 s3fs，到 AWS 后来推出的 Mountpoint for Amazon S3，再到今天的 S3 Files，S3 “像文件系统一样被访问”这条路，其实已经走了很多年。  

 AWS 在对象存储之上增加了一层基于 EFS 的文件系统访问面，使原本只能通过对象接口访问的数据，也能以目录、文件和挂载点的形式被计算节点直接使用；而文件系统与 S3 之间的数据变化，则由服务在后台自动同步。  

原理：  
作用域如何确定，首次访问会导入什么，哪些请求会进入高性能层，写入后又会如何同步回 S3。  
![758](assets/S3%20Files调研/file-20260506103651174.png)
上述是EC2 挂载现有 S3 bucket 为例，真正需要看清的不是挂载命令本身，而是挂载之后数据会如何被导入、访问与同步。  
- 先确定作用域：导入全量 S3 桶，还是指定部分目录？
两者皆可。S3 Files 支持将整个 S3 存储桶作为文件系统挂载，也支持通过 Prefix（前缀）限制作用域，例如只挂载 s3://my-bucket/data/ml/ 目录下。  但从实践上看，更推荐在创建 S3 Files 时就把作用域限定到明确的 prefix，而不是在一个过大的存储桶上再做后置控制

```bash
sudo yum -y install amazon-efs-utils
sudo mkdir /mnt/s3files
# 在计算节点上使用 S3 Files 时，AWS 提供了定制的挂载客户端 amazon-efs-utils。挂载时使用的并不是存储桶名称，而是 AWS 为 S3 Files 分配的 file system ID。
sudo mount -t s3files fs-1234567890abcdef0:/ /mnt/s3files
```
- 首次访问时会发生什么：导入触发方式与大小阈值
S3 Files 并不会在挂载后立即把整个数据集搬入高性能层。它的数据导入由访问事件触发，
    - 默认模式是 ON_DIRECTORY_FIRST_ACCESS：当你第一次访问某个目录时，系统会导入该目录下文件的元数据，并将符合条件的小文件数据异步导入 EFS 高性能层。  
    - 如果配置为 ON_FILE_ACCESS，则首次遍历目录时只导入元数据，只有在文件第一次被实际读取时，数据才会进入高性能层。这种方式更节省空间和导入成本，但首读延迟也会更高。  

 默认情况下，只有小于 128 KB 的文件才会在导入时进入高性能层；更大的文件通常只导入元数据，内容仍然主要通过 S3 获取。换句话说，S3 Files 优先优化的是小文件和低延迟访问，而不是把所有数据都预热到高性能层中。
- 同步周期与冲突解决机制    
S3 Files 会在后台自动维护文件系统与 S3 之间的双向同步。S3 侧发生变化后，文件系统视图会随之更新；而在计算节点上的写入，则会先落到 EFS 高性能层，再由后台批量同步回 S3。默认情况下，系统会对修改进行一段时间的聚合，再执行回写。

冲突处理的原则也很明确：S3 始终是 Source of Truth。如果文件系统侧的修改尚未同步回 S3，而对应对象已经在 S3 中被其他应用更新，系统会以 S3 中的最新版本为准，并将冲突文件移入 .s3files-lost+found-* 目录。  

**S3 Files 的性能边界与成本结构：**  
1. EFS 高性能层的占用、回收与成本
S3 Files 的高性能层并不是按容量上限做 LRU 淘汰，而是按访问时间进行生命周期管理。默认情况下，已同步到 S3 且 30 天未被读取的数据会从 EFS 高性能层中移除；这一时间由 daysAfterLastAccess 控制，可配置范围为 1–365 天。
2. 大文件直读与随机读：其实是客户端在“穿透”读取
S3 Files 对大文件的处理，并不是把所有读取都留在 EFS 高性能层中完成。默认情况下，sizeLessThan 的值为 128 KB，它决定的是哪些文件会在导入时把数据放入高性能层；而对于已经同步到 S3 的数据，128 KB 及以上的读取会直接从 S3 流式返回。**S3 Files 的优化重点更偏向小文件和低延迟访问，而不是让大文件读取长期稳定命中高性能层。**
3. 顺序写的代价：大规模写入会引入额外流转成本
S3 Files 的写路径并不是直接落到 S3。所有写操作都会先进入 EFS 高性能层，再由后台同步回 S3。  
    - 数据流转成本：写入先进入高性能层，随后再同步回 S3。相比直接写入 S3，这条路径会多出一层中间流转开销。
    - 短期驻留成本：数据同步完成后，并不会立刻从高性能层中移除，而是要等到满足过期条件后才会清理。默认情况下，这意味着大批量写入产生的临时数据，可能在一段时间内持续占用 EFS 容量。  
4. 局部更新与目录操作：对象模型带来的放大效应
S3 Files 底层不对数据进行切块，而是尽量保持文件与 S3 对象之间的直接映射。这带来的代价是：一旦涉及大文件的局部随机写或追加写，应用层看起来只是一次很小的更新，底层同步回 S3 时却更容易放大为显著的对象写入与版本开销

目录重命名同样受 S3 扁平命名空间限制。S3 本身没有传统文件系统中的目录元数据，因此执行 rename 或 mv 时，S3 Files 不能只改一条元数据，而是必须在 S3 侧为目录中的每个文件写入新对象并删除旧对象。对于拥有千万级对象的目录，这会显著拉长同步时间，并增加 S3 请求成本；在同步完成前，文件系统视图与 S3 视图之间还可能暂时不完全一致。  

S3 Files 的优势在于原生接入、零数据迁移，以及对现有 S3 资产的良好兼容。它的代价则在于：一旦场景转向大文件读取、持续写入、频繁局部更新或大目录操作，性能和成本都会更快被放大。 


 方向：  
1. 保持文件与 S3 对象之间的直接映射，以换取对现有 S3 数据的透明访问能力，更强调对现有对象数据的原生接入与低改造成本
2. 以对象存储作为底层持久化介质，在其上构建独立的元数据与数据管理体系，使其更接近一个真正面向生产负载的分布式文件系统，比如juicefs，更强调在对象存储之上提供更完整、更稳定的文件系统能力，以承接训练、分析和数据生产等更重的生产型负载。

侧重点：  
1. 核心诉求是在不改动现有架构的前提下，让旧应用、Shell 脚本或传统软件直接以文件方式访问现有 S3 数据；或者需要一个通用的共享文件空间，且以只读、小文件、顺序读写为主，那么 S3 Files 会是更自然的选择
2. 业务逐步转向 AI 模型训练、数据生产、高性能计算（HPC）或大数据分析，开始面临千万级小文件、TB 级大文件随机读写，或者对 mmap、缓存命中率和整体吞吐有更高要求，那么就需要进一步评估另一类方案——即在对象存储之上构建独立文件系统能力的路线。相比强调透明访问现有对象的方案，这类架构通常更适合承接重负载和长期运行的生产型文件系统场景。

[S3 Files上线：AWS终于补上这块十年短板](https://www.163.com/dy/article/KQHVA86J05561FZY.html)
架构上，S3 Files做了三件事 ：  
1. 延迟加载（Lazy Loading）。挂载文件系统时，不预拉数据，只建立目录结构。第一次访问某个文件时，才从S3取数据到本地缓存。
2. 写时复制（Copy-on-Write）。修改文件时，不直接动S3里的对象，先在缓存层操作，显式调用fsync或卸载时才回写。这保证了S3对象的不可变性（immutability）不被破坏——S3的核心设计哲学保住了
3. 元数据分离。文件系统的inode、权限、时间戳等元数据，单独存在S3的元数据服务里，不和对象数据混在一起。这让ls、stat这类操作不用遍历整个bucket
最佳场景：  
1. 机器学习训练。大规模分布式训练需要共享数据集，检查点需要随机读写。S3 Files让多个计算节点同时挂载同一个bucket，像访问本地磁盘一样读写，但底层数据还是统一在S3。
2. AI Agent工作流。Agent需要频繁读写中间状态、日志、临时文件。POSIX语意让Agent框架（比如LangChain、AutoGPT的变种）不用改代码就能跑在S3上
3. 数据分析。Pandas、Polars、Spark这些工具原本假设数据在本地文件系统。S3 Files让它们直接读S3上的Parquet、CSV，不用先s3 cp到本地
4. 共享开发环境。团队共享一个代码仓库或数据集，每个人在自己的EC2上挂载同一个S3 Files系统，告别"我本地跑得好好的"问题
不适合的场景：  
- 高并发小文件写入。S3 Files的元数据操作还是有开销，每秒创建数万个空文件会卡死。
- 需要强一致性的实时系统。虽然S3 Files支持fsync，但跨区域的最终一致性（eventual consistency）模型没变。金融交易、实时竞价这类场景，还是得用专门的分布式文件系统。
- 成本敏感型冷存储。S3 Files的缓存层用EC2的本地存储，有额外的计算成本。如果数据一个月访问一次，标准S3 + 批量下载更便宜。


[Amazon S3 Files 实战：S3 终于能当文件系统挂载了，NFS 直接读写对象存储](https://www.cnblogs.com/AmazonwebService/p/19857536#commentform)
- S3 Files 是什么  
一句话：**把 S3 桶变成 NFS 文件系统，挂到 EC2/ECS/EKS/Lambda 上直接读写**。
底层用的是 Amazon EFS 引擎，延迟大约 1ms。支持 NFS v4.1+ 协议，所有标准文件操作都能用——创建、读取、修改、删除，跟本地文件系统一样。
文件系统上改了文件，几分钟内自动同步回 S3 桶。S3 桶上对象有变更，文件系统这边几秒就能看到  
- 核心特性：
    1. 1ms级延迟: 活跃数据缓存在高性能存储层，访问延迟约 1ms。冷数据直接从 S3 拉取，走大吞吐量通道。系统还有智能预取，会根据你的访问模式提前加载数据。
    2. NFS 挂载，零代码改造： 不需要改应用代码。原来读本地文件的程序，`mount` 之后直接指向 S3 数据目录就行。Python 的 `open()`、Shell 的 `cat`、`grep`、`sed` 都能直接用
    3. 自动双向同步[^7]
        - 文件系统 → S3：修改后几分钟内同步为新对象或新版本
        - S3 → 文件系统：桶上变更几秒可见（偶尔需要几分钟）
    4.  多计算资源并发： 多个 EC2、容器、Lambda 可以同时挂载同一个文件系统。用的是 NFS close-to-open 一致性模型[^8]，适合 AI Agent 协作、ML 训练流水线这种多节点共享场景。
    5. 细粒度缓存控制：可以控制哪些数据放在高性能存储层——全量文件还是只缓存元数据，按业务访问模式灵活配置。

CLI 完整流程：  
```bash
# 1. 创建 S3 文件系统（关联到已有的通用型桶）
aws s3 create-file-system \
  --bucket my-training-data-bucket \
  --file-system-name my-training-fs

# 返回类似：
# {
#   "FileSystemId": "fs-0aa860d05df9afdfe",
#   "BucketName": "my-training-data-bucket",
#   ...
# }

# 2. 创建 Mount Target（指定 VPC 子网和安全组）
aws s3 create-mount-target \
  --file-system-id fs-0aa860d05df9afdfe \
  --subnet-id subnet-0123456789abcdef0 \
  --security-groups sg-0123456789abcdef0

# 3. 等 Mount Target 状态变为 available
aws s3 describe-mount-targets \
  --file-system-id fs-0aa860d05df9afdfe

# 4. 创建挂载目录
sudo mkdir /home/ec2-user/s3files

# 5. EC2 上挂载
sudo mount -t s3files fs-0aa860d05df9afdfe:/ /home/ec2-user/s3files

# 6 读写验证
# 6.1 在文件系统中创建文件
echo "Hello S3 Files" > s3files/hello.txt

# 6.2 本地确认文件存在
ls -al s3files/hello.txt
# -rw-r--r--. 1 ec2-user ec2-user 15 Apr 13 08:00 s3files/hello.txt

# 6.3 等待几分钟，在 S3 侧确认同步
aws s3 ls s3://my-bucket/hello.txt
# 2026-04-13 08:01:04 15 hello.txt

# 6.4 内容一致
aws s3 cp s3://my-bucket/hello.txt . && cat hello.txt
# Hello S3 Files
```
