## 1.2 数据模型与基础约束  
### 1.2.1 存储模型：有序键值
- Key、Value 均为二进制字节数组，天然有序；
- 支持 Key 前缀范围扫描，非常适合构建复合索引、分层数据；
- 支持 `Versionstamp` 自动递增版本键，用于自增 ID 场景。

### 1.2.2 硬性事务 / 数据约束（设计取舍）  
1. **事务最大时长 5 秒**：事务从开启到提交不能超过 5 秒，长事务必须拆分为多个小事务；
2. **单事务总容量上限 10MB**：包含所有读写 Key/Value、冲突区间；
3. Key 最大 10KB，Value 最大 100KB：不适合直接存储图片、大文件，大对象需分片存储；
4. Sequencer 为全局单点：故障瞬间集群写事务短暂失败，但可快速自动恢复，牺牲极小可用性换取极简全局时序设计

| 优势                                    | 劣势                       |
|---------------------------------------|--------------------------|
| 真正的 ACID 事务 + 乐观并发控制 (OCC)            | 事务大小限制 10MB              |
| 客户端自动重试（Transact 内部循环）                | 事务超时默认 5 秒               |
| 服务端原子操作：Add（原子整数加）、AppendIfFits（原子追加） | Key ≤ 10KB，Value ≤ 100KB |
| 有序 KV 空间，高效范围扫描                       | 无 SQL 查询能力               |
| 亚毫秒级小读写延迟                             | OCC 高冲突场景重试率高            |
| ReadTransact 只读事务（不追踪冲突）              | 无服务端 GC                  |
| ClearRange 高效批量删除                     | —                        |
| GetReadVersion 全局有序版本号                | —                        |

#### 1.2.2.1 影响  
##### 1.2.2.1.1 严格的事务硬阈值：
递归删除超大目录、批量 rename、大目录 list、大量文件批量导入，**不能放在一个事务**，上层必须手动拆分、分页、循环重试；
JuiceFS 场景下：同一个文件持续随机覆盖写，chunk 索引列表持续膨胀，极易触碰 100KB Value 上限。
##### 1.2.2.1.2 SSI 串行快照隔离，乐观事务冲突代价极高  
FDB 默认最高隔离级别（Serializable Snapshot Isolation），采用**乐观并发控制，无悲观锁**。
- 同一目录下并发 create/unlink/rename，会产生大量事务冲突；
- 冲突事务直接 abort，上层需要不断重试；高并发元数据风暴下，吞吐量断崖下跌、尾延迟爆炸。 ==3FS或者JuiceFS如何解决==
> 典型场景：日志目录持续创建删除小文件、批量 rename。    
> 对比传统 CephFS MDS：可以通过分布式锁、目录分片缓解冲突，冲突不会直接导致事务大规模重试。  
##### 1.2.2.1.3 跨分片事务必须 2PC，天然带来延迟放大  
文件系统一次基础操作（`creat`）至少修改 2 组 Key：
`inode` + `dentry(父目录)`。
若两个 Key 落在 FDB 不同分片，触发**两阶段提交**，网络往返翻倍。
哪怕做 Key 布局优化，长期运行分片均衡迁移后，依然无法完全规避跨分片事务。  
##### 1.2.2.1.4 全局 Sequencer（TSO 时间戳）隐性单点瓶颈  
FDB 所有事务需要全局有序时间戳；Sequencer 可以快速故障切换，但**同一时刻只有一个主节点**。极端海量元数据写入场景下，Sequencer 会成为整个集群写吞吐上限。
#### 1.2.2.2 业务场景适配短板  
❌ 不擅长：海量小文件、高频随机写、重度目录并发
1. 小文件随机写性能偏弱
架构优势是**大文件顺序读写（AI 训练数据集场景）**；
大量小文件频繁创建、删除、覆盖写入，元数据 OPS 受 FDB 事务能力约束，远弱于专用并行文件系统。  
>  3FS 官方测试数据：4KB 小文件随机写性能显著低于传统商用并行存储。   
2. rename、跨目录操作成本高
POSIX `rename(old,new)` 是典型跨目录事务，需要修改多条 dentry 记录；一旦新旧目录落在不同 FDB 分片，开销成倍上涨。
很多实现（3FS）为了性能，**主动弱化完整 POSIX 语义**（例如不实时更新目录 mtime）换取吞吐量，无法满足强一致性通用业务。  
✅ 擅长场景：大文件、读多写少、AI 数据集、离线训练  

和传统方案横向对比总结：  

| 痛点            | 基于 FDB 的 KV 型文件系统      | CephFS（原生 MDS）        |
|---------------|------------------------|-----------------------|
| 事务实现          | 依赖 FDB SSI 乐观事务，冲突容易雪崩 | 自研分布式锁，悲观 / 乐观混合，冲突可控 |
| 元数据延迟基线       | 更高（多层网络转发）             | 更低                    |
| 扩展上限          | 受 FDB 集群整体吞吐约束         | MDS 可动态分片，成熟度高        |
| 小文件负载         | 劣势明显                   | 更加均衡                  |
| 大规模 rename 风暴 | 风险高                    | 更稳定                   |
| 运维组件          | 元数据集群独立部署，两套集群         | 统一一套 Ceph 集群          |
| 优势场景          | 大文件读多写少（AI 训练）         | 通用混合负载、中小文件业务         |

## 1.3 部署  
FDB 的一个关键设计是：**多个角色可以运行在同一个进程上**。
- **小集群（1~3 台机器）**：几乎所有角色都共驻在同一组进程上，`UnsetClass` 进程可以同时承担 Storage + Transaction 角色
- **中大集群**：通过 `ProcessClass` 做角色分离，例如：
    - `transaction` 类进程 → 承载 CommitProxy/GRVProxy/Resolver/TLog
    - `storage` 类进程 → 只承载 Storage Server
    - `stateless` 类进程 → 承载 DD/RK/CS 等单例角色
