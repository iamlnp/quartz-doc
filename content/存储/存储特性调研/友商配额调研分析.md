# 1 JuiceFS  

JuiceFS 实现了三层配额体系  

| 层次     | 类型常量                            | 限制维度       | 作用域            |
|--------|---------------------------------|------------|----------------|
| 卷级配额   | Format.Capacity / Format.Inodes | 空间 + Inode | 整个文件系统         |
| 目录配额   | DirQuotaType                    | 空间 + Inode | 指定目录子树         |
| 用户/组配额 | UserQuotaType / GroupQuotaType  | 空间 + Inode | 按 UID/GID 全局统计 |


| 场景                      | 行为                      | 开销           |
| ----------------------- | ----------------------- | ------------ |
| 目录配额首次设置（created=true）  | GetSummary 扫描该子树        | 与子树大小成正比     |
| 目录配额更新上限（created=false） | 只改 Max，不扫描              | O(1)         |
| 用户/组配额首次启用              | ScanUserGroupUsage 扫描全量 | 与整个文件系统大小成正比 |
| 用户/组配额更新上限              | 只改 Max，不扫描              | O(1)         |

将未启用配额目录A rename到启用配额的目录B下：  

| 目录 A 自身有配额 | 获取方式                                    | 开销       |
|------------|-----------------------------------------|----------|
| 是          | 直接读 dirQuotas[ino].UsedSpace/UsedInodes | O(1)，不扫描 |
| 否          | 调用 GetSummary 递归遍历 A 的整棵子树              | 与子树大小成正比 |

| 场景                                  | 是否扫描                                                 |
|-------------------------------------|------------------------------------------------------|
| 同目录下 rename（parentSrc == parentDst） | 不扫描，quotaSrc == quotaDst                             |
| 跨目录 rename 一个文件                     | 不扫描，直接 space = align4K(attr.Length), inodes = 1，O(1) |
| 跨配额域 rename 一个目录，但该目录自身有配额          | 不扫描，直接读缓存的 UsedSpace，O(1)                            |
| 跨配额域 rename 一个目录，目录无配额              | 扫描整棵子树                                               |
| 整个文件系统没有启用任何目录配额（DirStats == false） | 不扫描，quotaSrc/quotaDst 都是 0，相等                        |

扫描子树时，业务正在进行，扫描的结果也会不准？比如刚扫描完子目录A，A下然后进行创删读写，同时会不会因为加锁阻塞业务？
- 扫描读 `dirStats` 缓存时用 `RLock`（读锁），业务的 `updateDirStat` 用 `Lock`（写锁），两者互斥但持锁时间极短（只是 map 读写）
- `doReaddir(resolve=0)` 只读目录项列表，不读文件 attr，对引擎压力很小
- 扫描过程中**不会**阻止任何 Create/Write/Unlink/Truncate 操作

# 3 CubeFS
CubeFS 的配额统计不是实时递归回溯父目录，而是基于 inode 的 quotaId 直接归属统计。每个 inode在其扩展属性中记录了 quotaId，属于哪个配额组，统计时，直接根据 quotaId 进行分组累加，无需递归遍历父目录树。所以目录深度不会影响配额统计的性能。

inode 关联了 quotaId，统计就是 O(1) 的本地操作。在超大容量情况下，绝大多数操作，如写入、创建、删除只需本地 quotaId 的已用空间/文件数加减，无需全量扫描。仅在重启/快照恢复等极少数场景需要全量扫描分区内所有 inode，累加各 quotaId 的用量。  

配额判断和统计都是 O(1) 的本地内存操作[^1]，无需递归目录树或全局分布式锁。扩展性好，适合大规模分布式场景。不同 quotaId 可对应不同租户、项目、目录，实现资源隔离和精细化管理。

缺陷：
分区级统计，主控汇总极端情况下可能有短暂超配额。如果需要将整个目录树切换到另一个 quotaId，需要遍历并更新所有 inode 的 quotaId，操作量大。且分区重启/快照恢复时，需要全量扫描 inode 统计 quotaId 用量，极大分区下有一定资源消耗。[^2]
# 4 Qumulo  
闭源，Qumulo 只支持目录配额，
1. 配额跟随目录 inode，不是路径字符串
2. 是 “接近硬配额” 的实现，无传统 soft/grace 宽限期
3. 只做容量字节限制，不支持 inodes（文件数）配额
4. 嵌套目录配额
5. Snapshot 快照空间不计入目录配额统计

rename处理：  
1. 同目录 rename，只改目录项名字；**无任何子树扫描**；mv 立刻返回
2. mv 把带配额的目录移动到另一个父目录（跨父目录）： `mv /proj1/data /proj2/data`
    - mv 元数据操作瞬时完成，**不遍历 data 下千万文件**，不会卡住
    - data 目录的配额依然绑定该 inode id，配额 limit 不变
    - 如果 `/proj2` 本身也设置了父目录配额，移动完成后，**下一次后台周期扫描**才会把 data 的容量计入父 `/proj2` 的配额统计；**mv 瞬间不会立刻更新父配额数值**，存在几秒窗口延迟。 写入时校验也是依赖后台扫描出来的统计值，因此移动后短暂窗口，父配额的已用显示值会滞后

触发全量扫描场景：  
1. **新建配额的时候**：当你给一个已经存在大量数据的目录 `qq quota_create_quota --id <inode>`，此时会触发一次性完整递归扫描，算出初始 usage；这个操作会消耗元数据节点 CPU，大目录会耗时
2. 后台周期性定时扫描（所有已配置配额的 inode 轮询）
3. 内部某些元数据修复事件

# 5 CephFS  
CephFS 允许在**任意目录**上设置配额，限制该目录层级下存储的**字节数**或**文件数**，不支持用户配额  

## 5.1 整体架构  
```bash
┌─────────────────────────────────────────────────────┐
│                    客户端 (Client)                     │
│  ┌──────────┐  ┌───────────┐  ┌──────────────────┐  │
│  │ write()  │  │ create()  │  │ mkdir/mknod/link │  │  ← 写入/创建前检查配额
│  └────┬─────┘  └─────┬─────┘  └────────┬─────────┘  │
│       │              │                  │             │
│       ▼              ▼                  ▼             │
│  is_quota_bytes  is_quota_files                     │
│  _exceeded()     _exceeded()                        │  ← 配额判断
│       │              │                              │
│       ▼              ▼                              │
│  check_quota_condition() — 遍历配额祖先链             │  ← 向上查找最近的配额目录
│       │                                             │
│       ▼                                             │
│  get_quota_root() — 通过 SnapRealm 链查找            │  ← 定位配额根
│                                                     │
│  handle_quota(MClientQuota) — 更新本地配额/用量数据    │  ← 接收 MDS 推送
└───────────────────────┬─────────────────────────────┘
                        │ MClientQuota 消息
                        ▼
┌─────────────────────────────────────────────────────┐
│                    MDS (MDCache)                      │
│  ┌──────────────────────────────────────────────┐   │
│  │ broadcast_quota_to_client()                         │   │
│  │  - 监控 rstat.rbytes/rsize() 变化             │   │
│  │  - 接近/超过配额时推送 MClientQuota 给客户端    │   │
│  │  - 阈值触发: 超过 87.5% 或变化量超过 1/16      │   │
│  └──────────────────────────────────────────────┘   │
│                                                     │
│  parse_quota_vxattr() — 解析配额扩展属性              │
│  create_quota_realm() — 为配额目录创建 SnapRealm     │
└─────────────────────────────────────────────────────┘
```
## 5.2 实现梳理  
1. MDS → 客户端的配额推送： `MDCache::broadcast_quota_to_client()`
MDS主动推送，不存在定时器或固定周期，通知时机完全取决于**rstat 何时发生变化**（即文件系统元数据操作完成时），然后在 `broadcast_quota_to_client()` 内部再根据之前分析的阈值条件（L2110-L2132）决定**是否真正发送** `MClientQuota` 消息给某个客户端。如果用量没有变化或变化量未达到阈值，就会  `continue` 跳过：
- 有文件创建/删除/大小变更导致目录的递归统计量更新时
- 当文件/目录的 link/unlink 操作需要把 `rstat` 从 dirfrag 投影到 inode 时
- 配额属性被修改时

2. 递归统计机制
配额依赖 [nest_info_t](file:///Users/liunaipeng/Documents/code/ceph/src/include/cephfs/types.h#L146-L163) 进行**递归统计**，MDS 通过 `nestlock` 维护这些递归统计数据，子目录的变更会逐级向上传播到配额目录。  

3. 客户端配额检查
get_quota_root()通过 **SnapRealm 链**向上遍历，找到最近的设置了配额的祖先目录  

4. 禁止跨不同配额域的rename
5. 当挂载根目录设有字节配额且 `client_quota_df=true` 时，statfs会将配额信息映射到文件系统空间报告

## 5.3 缺点和局限性

| 缺点      | 说明                                                      |
| ------- | ------------------------------------------------------- |
| 非对抗性    | 完全依赖客户端合作，恶意/修改过的客户端可以无视配额写入任意数据，不能用于不可信环境              |
| 不精确     | 配额超限后才会通知客户端停止写入，存在"超额"窗口期（通常约 10 秒），实际超额量取决于写入速度       |
| 客户端侧执行  | MDS 不强制拒绝写入，仅在客户端侧检查，安全性较弱                              |
| 内核版本要求  | 内核客户端需要 Linux 4.17+ 且集群版本为 Mimic+                       |
| 路径挂载限制  | 与基于路径的访问限制配合使用时需格外小心——客户端必须能访问配额目录的父目录才能执行配额检查          |
| 快照不计入   | 快照中已被删除或修改的文件数据不计入配额，可能导致实际存储超过配额限制                     |
| 异步通知    | MDS 通过阈值触发推送 MClientQuota，不是实时同步，存在延迟                   |
| 无服务端硬限制 | MDS 端没有在操作处理路径上做配额硬检查（如 Server.cc 中无 EDQUOT 返回），完全信任客户端 |
| 单客户端视角  | 多个客户端并发写入时，每个客户端看到的 rstat 可能有延迟，可能导致多个客户端同时超额写入         |



[^1]: 存疑：配额判断按理势必涉及递归查询父目录的quota配置，只是更新配额不用递归

[^2]: rename同样开销非常大，juicefs和cubefs面向云场景，rename操作不多，通用文件系统必须要考虑rename的性能问题
